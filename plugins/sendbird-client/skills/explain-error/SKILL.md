# /sendbird-client:explain-error

Resolve every plugin-owned path below from `${CLAUDE_PLUGIN_ROOT}`. Where that variable is empty (Codex does not set it for shell commands), the plugin root is the folder two levels above this SKILL.md.
A look-up (what a code means, its triggers, the documented fix) needs no agent and changes no file. When the customer asks for code inspection or a code change, resolve the platform agent with `bash "${CLAUDE_PLUGIN_ROOT}/tools/routing/route-agent.sh" <project-dir> code`. Hand work to that agent by calling the `Agent` tool once with the agent as Claude Code lists it: this plugin's name, a colon, then the name the router printed (for example `sendbird-client:sendbird-ios-agent`). In Codex, which has no `Agent` tool, run that agent's launcher skill instead (for example `$sendbird-client:sendbird-ios-agent`) and start the agent only as that skill says; it sets the model and settings the agent needs. Do not do the agent's part yourself, even in a small project: write or edit no project source file in this session, before or after the hand-off, also when the customer confirms a change in a later turn. If the hand-off fails, say that this part was not done. When the agent reports, your final answer carries its changed files, every check line, and its symbol, source, and version table as the agent wrote them (`docs/AGENT_CONTRACT.md` section 6); shorten the wording only.

Detect the customer's platform and installed SDK version before interpreting a numeric code. Never carry a symbol or description from one platform's error enum to another platform.

Map an error to meaning + fix (Intent A — lookup).

## Steps
1. Run `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/detect.sh" <project-dir>` and keep the platform and installed SDK version. Only when it finds no project, ask which platform (in a non-interactive run, cover each platform's table instead).
2. Look up the code in the verified table `knowledge/curated/<platform>/cross-cutting/errors.md`. Interpret it only with the detected platform and resolved SDK version because the same number can map to a different symbol or description on another platform.
3. For triggers and fixes, and for a symptom with no code ("push never arrives", "channel missing from the list"), check `knowledge/curated/<platform>/cross-cutting/troubleshooting.md`: symptom, cause, and fix from solved public cases, each fix re-checked against the pinned SDK. Entries marked community were resolved by users, not Sendbird staff; say so when you use one.
4. If the code isn't in the curated table: check `${CLAUDE_PLUGIN_ROOT}/knowledge/imports/<platform>/<product>/error-codes.md` when present, else read the customer-local SDK error enum via `bash "${CLAUDE_PLUGIN_ROOT}/tools/local-sdk/read-surface.sh" <project> <product> [resolved-version]`, else search version-matched official docs.
5. Report: code, the detected platform's symbol (e.g. in an iOS project, 400302 = `accessTokenNotValid`), meaning, common triggers, fix (codegen handed to the platform agent for in-scope products), related docs link — all cited. Cite the curated `errors.md` row and the `troubleshooting.md` entry you used as `knowledge/curated/<platform>/cross-cutting/<file>.md` with the line or heading, before any link; a link that the entry cites (a public source file, a community case) may follow it but never replaces it, and cite a page only when you read it in this run. Name only the detected platform's symbol; add other platforms' names only when the customer asks for them. Change no file in this step: write the fix only when the customer asks for it or confirms it, through the platform agent as the top of this skill says. This skill is read-only, so a run whose request does not ask for the fix ends with `status: "completed"`: put the offered code change under `nextSteps` and add no `apply-fix` or other question (`docs/AGENT_CONTRACT.md` section 7). Session-expiry codes route to `products/auth.md` refresh patterns. Rate-limit and plan-quota codes (for example 500910): give the back-off fix from `errors.md`, then point to the pricing page and the dashboard as `knowledge/curated/common/pricing-quotas.md` says; never state a limit number.

## No-Fabrication
Only report error codes/meanings present in a verified source. If the code isn't found, say "not found in <searched sources>" and suggest the docs — never invent a meaning. The same holds for a constant name: when it is not in the verified table, the next step you offer is a source check (`read-surface.sh` on the customer's installed SDK, or the place where they saw the name). Whether their compiler, IDE autocomplete, or a test call accepts the name is not a way to verify it.
