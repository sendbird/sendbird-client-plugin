# /sendbird-client:add-feature

Resolve every plugin-owned path below from `${CLAUDE_PLUGIN_ROOT}`. Where that variable is empty (Codex does not set it for shell commands), the plugin root is the folder two levels above this SKILL.md.
Resolve the platform agent with `bash "${CLAUDE_PLUGIN_ROOT}/tools/routing/route-agent.sh" <project-dir> code`. Hand work to that agent by calling the `Agent` tool once with the agent as Claude Code lists it: this plugin's name, a colon, then the name the router printed (for example `sendbird-client:sendbird-ios-agent`). In Codex, which has no `Agent` tool, run that agent's launcher skill instead (for example `$sendbird-client:sendbird-ios-agent`) and start the agent only as that skill says; it sets the model and settings the agent needs. Do not do the agent's part yourself, even in a small project: write or edit no project source file in this session, before or after the hand-off, also when the customer confirms a change in a later turn. If the hand-off fails, say that this part was not done. When the agent reports, your final answer carries its changed files, every check line, and its symbol, source, and version table as the agent wrote them (`docs/AGENT_CONTRACT.md` section 6); shorten the wording only.
Before anything else, check every product the request names (AI Agent, its messenger or launcher, is `ai-agent`; the others are `chat`, `uikit`, `calls`, `desk`, and `live`) with `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/resolve-products.sh" <project-dir> --check <product>`, one run per product. Printing the scope without `--check` is not this check. When it exits 1, change nothing and hand nothing to an agent: say what it printed. Only for "out of configured scope" add that `SENDBIRD_PRODUCTS` or `enabledProducts` in `.sendbird-client/profile.json` sets the scope; for "not covered by this plugin" say that this plugin does not cover that product and name the products it covers, and never suggest `SENDBIRD_PRODUCTS` or `enabledProducts`, which cannot add it; for "not available on this host" give the reason it printed and suggest neither; a non-interactive run ends with `status: "declined"`.

Add one feature to an existing integration.

## Steps
1. Run `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/detect.sh" <project-dir>` and resolve platform, host, product, and installed SDK versions. If an ambiguity changes the emitted code, ask one focused question before handing off, for example which UI to build with when the host is `hybrid` (docs/AGENT_CONTRACT.md section 1).
2. For every feature request, in this session and before the hand-off in step 3, look things up in this order, as ui-customize does: first read the matching curated sections (Wired knowledge below), then run `bash "${CLAUDE_PLUGIN_ROOT}/core/commands/search-discussions.sh" <owner/repo> <English keywords>` once on the UIKit repository for the detected platform and host (from `config/plugin-config.json` `.repos`, for example `.repos.ios.uikitUikitHost` on iOS UIKit, `.repos.android.uikit` on Android, `.repos.js.uikitReactNative` on React Native). Put the curated sections and the discussion results, or the `NOT RUN: <reason>` line, in the agent's brief; the agent then checks the customer-local SDK, public source, and docs. Label what a discussion says as community signal; when the command prints `NOT RUN: <reason>`, say in the answer that discussions were not searched and why.
3. Hand off to the platform agent to splice the matching template under `templates/<platform>/<host>/<product>/` and wire imports/delegates/hooks. List that folder first and name its files in the brief, word for word, with the instruction to keep each template's `source:` comment at the top of the file the agent writes from it; the final answer's source table names the same template path. A file written for that product without the template's source comment does not finish the request.
   When the project has no Sendbird UIKit package and the feature adds or changes a chat screen built on the Chat SDK, the brief also tells the agent to type-check the files it wrote once they are written: `bash "${CLAUDE_PLUGIN_ROOT}/tools/verify/check-written.sh" <project-dir> <every .ts, .tsx, .kt, .java, and .swift file written>`, fix the errors it lists in those files, and run it again, up to three runs (contract section 3, "Type-check the Chat SDK screens you wrote"). A UIKit project does not run it.
4. Report as `docs/AGENT_CONTRACT.md` section 6 lists, whether the agent or you made the change: the task envelope, the changed files, each section 4 check (with `typecheck` when the step above ran it) and each check of this feature (for example handler removal on the screen that adds it) as pass, fail, or not run with file:line, and the symbol, source, source version, and verification method table. Cite the source that contains each symbol, not a related docs page. Suggest `/sendbird-client:run-check` once (suggest only). In a non-interactive run, end with the run summary (`skill: "add-feature"`, the checks under `checks`).

## Wired knowledge (populated and cited)
- Per-product API: `knowledge/curated/<platform>/products/<product>.md` — channel/message (chat), prebuilt screens (uikit), dial (calls).
- Verified base templates exist for every product on all six hosts: ios/uikit, ios/swiftui, android/view, android/compose, js/react, js/react-native, under `templates/<platform>/<host>/<product>/` (each dir's `_README.md` has splice steps + variations).
- Chat message features have templates on all six hosts, under `templates/<platform>/<host>/chat/` (the `_README.md` there has per-feature splice steps):

  | Feature | ios/uikit, android/view | ios/swiftui | android/compose | js/react, js/react-native |
  |---|---|---|---|---|
  | Send an image or file, upload progress, cancel, resend a failed one | `FileMessageSender` | `FileUploadModel` | `FileUploadViewModel` | `FileMessageUpload.ts` (no upload progress on React Native) |
  | Edit and delete your own messages, other members' edits and deletes | `MessageEditing` | `MessageActionsModel` | `MessageActionsViewModel` | `MessageEditing.ts` |
  | Unread counts (total badge, per channel, mark as read) | `UnreadCount` | `UnreadCountModel` | `UnreadCountViewModel` | `UnreadCount.ts` |
  | Typing indicator and read receipts | `TypingAndReadReceipts` | `ChannelActivityModel` | `ChannelActivityViewModel` | `TypingAndReadReceipts.ts` |
  | Thread replies (load, reply, new replies) | `MessageThreads` | `ThreadModel` | `ThreadViewModel` | none yet: `knowledge/curated/js/products/chat.md` "Message threads" |

  A feature from this table is done when it works on screen: the agent follows every splice step in the folder's `_README.md`, not only the helper file. For files that means the picker that chooses the image or document, the permission it needs, file messages shown in the message list, and a resend action on a failed one; a helper that nothing in the app calls, or a picker left as a to-do, does not finish the request. On React Native, also cite `knowledge/curated/js/hosts/react-native.md` "Sending a file (no `File` in React Native)" for the file object and pick the picker package version from the project's `react-native` version (its "Version compatibility checklist").

- Calls (a voice or video call, accept or decline an incoming call, sign out of Calls): `templates/<platform>/<host>/calls/` on all six hosts; the folder's `_README.md` has the permissions and splice steps, and `templates/js/react/calls/DirectCallPanel.tsx` is a ready call screen for React. On iOS, Android, and React Native, incoming calls need push even while the app is open; dialing out does not. When this run does not wire that push, `manualSteps` lists the push credentials and names the `calls-incoming` skill as the next step (`knowledge/curated/<platform>/products/calls.md` "Manual steps").
- If the specific feature isn't templated yet, derive it from the curated doc's cited sections or the customer-local SDK surface — never from memory.

## No-Fabrication
Every API in the inserted code must be verified and cited. If the feature/template is not yet verified for this platform+host, say so and offer the verified docs link rather than inventing code. Discussions are community signal, labeled as such.
