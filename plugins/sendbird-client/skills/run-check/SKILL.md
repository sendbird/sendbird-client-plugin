# /sendbird-client:run-check

Resolve every plugin-owned path below from `${CLAUDE_PLUGIN_ROOT}`. Where that variable is empty (Codex does not set it for shell commands), the plugin root is the folder two levels above this SKILL.md. A shell command that only reads or checks files exits 0 when a file it looks for is missing (`if [ -f <file> ]; then cat <file>; fi`, or `|| true` after an optional read), and quotes separator lines (`echo '=== name'`: zsh, the default macOS shell, treats a word that starts with `=` as a command name). Otherwise a normal check is shown to the customer as a failed command.
For a question about the project's sign-in or connect code, resolve the platform agent with `bash "${CLAUDE_PLUGIN_ROOT}/tools/routing/route-agent.sh" <project-dir> code`.

Runs the app for real. This is the only skill that builds and launches the customer's project, and it does so only because the customer asked.

## When to run
- Only when the customer asked to run or check the app for real (this command, or a request such as "check that it really works"). Never start it from another skill or as a verification step of setup, add-feature, or upgrade-sdk; those suggest it instead.
- Supported hosts are the ones the runtime harness supports: React web (`react`), iOS UIKit and SwiftUI apps built from an XcodeGen `project.yml` (`ios-uikit`, `ios-swiftui`), Android View and Compose apps with a Kotlin-DSL `app/build.gradle.kts` (`android-view`, `android-compose`), and React Native apps that have their `ios/` and `android/` native projects (`react-native`, one platform per run: `--platform ios` or `--platform android`). For a React Native project without the native project of that platform, Flutter, Unity, .NET, Unreal, a hybrid project, or anything else, say the run check does not support that project yet and stop.

## Steps
1. **Host.** Run `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/detect.sh" <project-dir>` and map platform and host to a harness host (js/react → `react`; js/react-native → `react-native`; ios uikit or swiftui → `ios-uikit` or `ios-swiftui`; android view or compose → `android-view` or `android-compose`). Anything else is not supported (see above).
   - Direct chat: when the app has no channel list and a button opens a 1:1 conversation with one fixed user (for example "Chat with seller" with the seller's user ID in the code), add `--direct-chat <that user ID>` to every `run.sh` command below; it works on every host, React and React Native included. Take the ID from the app's code; when the code gets it at run time (from a product, a server, or a route), ask the customer which user ID to use (non-interactive: stop with `status: "needs_input"` and one question, id `direct-chat-user`). User B is then that user, not a generated one: B connects once before the run so A's button can invite them, A presses the button, the conversation must open by itself, A sends, B finds A's message in the 1:1 channel the app made, and B replies, which A must see.
   - React Native, non-interactive (`SENDBIRD_NONINTERACTIVE` is set): never ask which platform. Use the platform the request names; when it names none, run both, iOS first and then Android, each as its own run. Do not end a turn on a platform question in this mode.
   - React Native: run on the platform the customer names. In an interactive run only, when they name none, ask once: iOS, Android, or both (both is two runs, one after the other, each with its own preflight and results folder). Non-interactive (`SENDBIRD_NONINTERACTIVE`): the platform the request names; when it names none, both. Add `--platform <ios|android>` to every `run.sh` command below. The harness builds a release build with the JavaScript bundled in, so the customer does not start Metro.
   - The platform question asks only for the platform. Do not ask for the go-ahead of step 4 in the same question. An answer that names a platform ("iOS", "both", "둘 다요") settles the platform and is never the go-ahead: continue with step 3 and ask the step 4 question next.
2. **Sign-in without tokens.** The check signs in two new test users with a user ID only. Read the project's Sendbird connect call (the platform's `knowledge/curated/<platform>/products/auth.md` shows the forms). If the app passes an access or session token, or gets one from its own server before connecting, report that the run check cannot sign in to an app that requires tokens and stop. The Sendbird app itself must also allow connecting with a user ID only; when it does not, the run fails at `connect` with an error code (step 6).
3. **Preflight.** Run `bash "${CLAUDE_PLUGIN_ROOT}/tools/runtime/run.sh" <project-dir> --host <host> --check`. It copies, installs, and builds nothing, and prints JSON: `appId.from` (where the App ID comes from: `SENDBIRD_APP_ID`, the project's `profile.json`, or its `sendbird.json`, which the Sendbird CLI writes; the value is never printed), `appIdHow`, `signIn`, the `checks` it will run, `missing`, and `notes` (what it will install and build). When `ready` is false, report each `missing` entry and what would fix it, and stop:
   - no App ID: the customer sets `SENDBIRD_APP_ID` or confirms the App ID with `/sendbird-client:setup` (stored as `appId` in `.sendbird-client/profile.json`);
   - a tool not found (Xcode, XcodeGen, CocoaPods, a JDK or Android SDK, an emulator image, Node): name it; do not install it;
   - no sign-in hook: the harness signs in through the app's `onLoginSucceeded(userId)` (the sign-in hook the setup skill fills) or the app's own sign-in form; without one there is nothing it can drive.
   - Non-interactive (`SENDBIRD_NONINTERACTIVE`): when the App ID is the only `missing` entry, stop with `status: "needs_input"` and one question, id `app-id`, asking for it through `SENDBIRD_APP_ID`. Any other `missing` entry ends the run with `status: "failed"` and `reason` naming each entry. Nothing is run in either case.
4. **Go-ahead.** Tell the customer, from the preflight `notes`, what will happen: the project is copied to a temporary folder and never changed; the listed tools are installed outside the project; the app is built and launched (browser, simulator, or emulator; iOS and Android builds take several minutes); two test users with generated IDs (`rt-<host>-a-…`, `rt-<host>-b-…`) sign in to the customer's Sendbird app, open a channel, and send messages, and a third (`rt-observer-…`) connects only to see that user A is online. These users, their channel, and the messages stay in that Sendbird app; the check does not delete them. The results and screenshots go to the plugin's state folder `.sendbird-client/` in the project (detect.sh already keeps its profile there): say that this folder is the plugin's, not the app's, and should not be committed: tell the customer to add `.sendbird-client/` to the project's `.gitignore` when it is not listed there yet (the check itself changes no project file). With `--direct-chat`, say instead that user B is the named user (`directChat` in the preflight), who connects and sends one reply as that user in a new 1:1 channel with A. Then ask once whether to go ahead, and wait for the answer: the run in step 5 never starts in the same turn as this question.
   - Consent (docs/AGENT_CONTRACT.md section 7): the request itself already gives the go-ahead when it allows building and running the app, in any language, for example "you have my go-ahead to build and launch it", "go ahead and run it", "빌드하고 실행해도 돼", "실행해 봐도 돼요", or "돌려 봐도 괜찮아". Then tell the customer what will happen and continue to step 5 without asking. A yes to the question counts the same way: "yes", "go ahead", "네", "응", "좋아요", "진행해 주세요". Asking for the check is not that consent: "check that it really works", "실제로 되는지 확인해 줘", or "run-check 해 줘" start this skill and still end at the question. "No", "아니요", or "나중에" runs nothing.
   - Non-interactive (`SENDBIRD_NONINTERACTIVE`): go ahead only when the request itself gives the go-ahead as above. Otherwise run nothing and stop with `status: "needs_input"` and one question, id `run-check-go-ahead`, options `yes` and `no`; the caller runs again with `run-check-go-ahead=yes`.
   - The go-ahead is a yes to this question, asked on its own after the platform is settled, or a request that already allowed the build. An answer to another question, such as the React Native platform ("둘 다요", "both"), is not the go-ahead: ask this question and end the turn without starting step 5.
5. **Run**, only after the go-ahead from step 4: `bash "${CLAUDE_PLUGIN_ROOT}/tools/runtime/run.sh" <project-dir> --host <host> --go-ahead --out <project-dir>/.sendbird-client/run-check/<UTC time, e.g. 20261014T101500Z>` (React Native: add `--platform <platform>` and end the folder name with `-<platform>`) with a Bash timeout of at least 10 minutes (React Native: 30 minutes; a first run installs its pods or Gradle dependencies). Pass `--go-ahead` only when the customer said yes or the request gave the go-ahead (step 4); without it the tool copies and builds nothing and exits 64 with a line that asks for it, and that line is never a reason to add the flag yourself. The tool reads the App ID itself; never pass it on the command line, echo it, or write it anywhere. Exit codes: 0 pass, 1 fail, 2 skipped (a tool or device was missing), 64 bad arguments or no `--go-ahead`.
6. **Report** from `<out>/runtime.json`:
   - a table of every step with pass, fail, or not run and its detail: `sign-in`, `chat-screen`, `connect`, `channel`, `message-a-receives`, `message-a-sends`, then `message-b-screen` (React) or `message-a-live` (iOS, Android, React Native), `errors`. With `--direct-chat` the steps are `sign-in`, `connect`, `chat-screen` (the button A pressed), `channel` (the conversation opened by itself), `message-a-sends`, and `message-a-live` on every host, and `channel-members` fails when the channel the app made holds anyone besides A and B. A step with `ok: null` did not apply (an app without UIKit screens checks `connect` only); report it as not run, never as passed;
   - React Native: one table per platform, each under its own heading, never one table with a column per platform. A run of one platform has only its own heading and table; a run of both has both, iOS first:

     ```
     ### iOS (results folder <out>-ios)
     | Step | Result | Detail |
     |---|---|---|
     | sign-in | pass | ... |

     ### Android (results folder <out>-android)
     | Step | Result | Detail |
     |---|---|---|
     | sign-in | pass | ... |
     ```
   - when `messageSteps.run` is false, say in one line that the channel and message steps did not run and why (`messageSteps.why`, which names the file whose Chat SDK code sends messages when there is one). If the app has its own chat screens built on the Chat SDK, offer to run again with `--chat-screens` (`messageSteps.enableWith`); the harness then drives those screens as it drives UIKit ones (on React it finds the channel list by the `sb_channel_list` test id, else a list or an empty-list line on screen, and the message input by `sb_message_input`, else a text input named for messages);
   - the test user IDs (`users.a`, `users.b`), the results folder, and the screenshots folder `<out>/screens/`;
   - on a failure: the first failed step, its detail, and the log file in `<out>` that has more. A connect failure that names an error code: look the code up in `knowledge/curated/<platform>/cross-cutting/errors.md` and cite it. Do not paste raw logs; they are stored with the App ID removed, but quote only the lines you need. The tool's output and files show the App ID as `<app-id>`; keep it that way, and never write a Sendbird host name or other value that holds the App ID into the answer. When a `message-a-sends` detail says the sender's own view has the message, the server accepted A's message and does not show it to B: tell the customer to check the Sendbird app's message filters (the run's texts are short English words and a six-digit number).
   In a non-interactive run, end with the run summary (`core/schemas/run-summary.schema.json`, `skill: "run-check"`): `completed` when every check passed, `failed` with the first failed step as `reason`, `declined` for an unsupported project or an app that requires tokens. `changes` is empty: the results folder belongs to the plugin, not to the app.

## Wired knowledge
- Harness: `tools/runtime/run.sh` (and `--check`), `tools/runtime/lib/appid.py` (how the App ID reaches the copy: an environment variable, a build setting, a Gradle property, a placeholder in a config file, or the App ID the config already holds when it matches), `tools/runtime/lib/peer.mjs` (user B).
- Connect forms and tokens: `knowledge/curated/<platform>/products/auth.md`. Error codes: `knowledge/curated/<platform>/cross-cutting/errors.md`.

## No-Fabrication
Report only what `runtime.json` and the logs show; never describe a skipped or not-run step as passed, and never guess why a step failed beyond what the detail and logs say — cite the error code table when a code appears. If the reason is not in the output, say "I don't know — here's what I checked" and name the files you read.
