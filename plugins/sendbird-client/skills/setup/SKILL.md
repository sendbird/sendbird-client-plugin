# /sendbird-client:setup

Interactive first-integration wizard.

Resolve every plugin-owned path below from `${CLAUDE_PLUGIN_ROOT}`. Where that variable is empty (Codex does not set it for shell commands), the plugin root is the folder two levels above this SKILL.md.
Resolve the platform agent with `bash "${CLAUDE_PLUGIN_ROOT}/tools/routing/route-agent.sh" <project-dir> code` before delegating.
Resolve the active product scope with `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/resolve-products.sh" <project-dir>` and decline out-of-scope products.

## Steps
1. Detect the project: run `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/detect.sh" <project-dir>` every time. Resolve platform, host, packageManager, deploymentTarget, lifecycle, products. If any Tier-1 fact is `unknown` or host is `hybrid`, ASK the customer once — never guess.
2. Resolve `app_id`: env `SENDBIRD_APP_ID` > `.sendbird-client/profile.json` (`appId` field) > ask. After the customer confirms it, **persist it** into `.sendbird-client/profile.json` (`appId`) so it is asked only once per project — App IDs are not secret. NEVER store session/access tokens anywhere (tokens stay in env at runtime).
   - To see which `SENDBIRD_*` variables are set, list names only with `env | grep -o '^SENDBIRD_[A-Z0-9_]*='` (a token such as `SENDBIRD_API_TOKEN` may be among them), then read each value you need with its own `printenv <NAME>`. macOS `printenv` reads only the first name, so `printenv SENDBIRD_NONINTERACTIVE SENDBIRD_APP_ID` never shows the App ID.
3. Hand off to the platform agent (`sendbird-ios-agent` / `sendbird-android-agent` / `sendbird-js-agent`) for code edits. Pass the customer's request and the detected facts. Leave the install and the App ID mechanism to the agent, which follows `docs/AGENT_CONTRACT.md` section 3, and keep its choices on those when it returns.
4. The agent installs the SDK dependency, inserts initialize + connect in the correct lifecycle entry, and (optionally) scaffolds a first screen from `templates/<platform>/<host>/<product>/`.
   - iOS: install via Swift Package Manager. Use CocoaPods only if the project already has a `Podfile`; never create one or run `pod install` on a fresh/SPM project.
   - If the project already uses Chat SDK v3 or UIKit v2, ask the customer whether to upgrade first, and follow `knowledge/curated/<platform>/cross-cutting/migration.md` when they agree.
5. Output the edit diff + a product-specific next-step checklist; suggest `/sendbird-client:verify-integration`.

## New app (empty folder)
Use this when the request is to create a new app, or the project folder is empty (detection finds no platform). The app starts from the catalog starter in step 4, never from a project generator such as `npm create vite`, `create-react-app`, or `create-next-app`: the starters already have the sign-in code (`onLoginSucceeded`, `onLogout`) that the rest of setup fills in.

1. Read the questions from `${CLAUDE_PLUGIN_ROOT}/core/catalog.json`. Drop options whose `product` is outside the active scope (`resolve-products.sh`), and drop a question with no options left. Skip a question whose `when` does not match the answers so far; a `when` on a `multi` answer matches when any chosen option is listed (`products=chat,calls` matches `"when": { "products": ["chat"] }`). A `required` question with one option left is not asked: that option is its answer (for example `products` when the scope has Chat but not Calls, or `chat-ui` when UIKit is out of scope). Leave out a question with `"offered": false`; that feature is not offered in new-app setup for now. If the request itself names that feature (for example in `notes`), build it as usual, unless its product is not supported yet (`resolve-products.sh --check <product>` reports `not supported yet`); that product is declined, never built.
2. Get the answers:
   - Answers the request already gives. The request is the customer's own message, not only the arguments this skill was started with: those can leave the SDK name out, so read both. Do not ask a question the request already answers:
     - `chat-ui=chat-sdk` (and `chat` in `products`) when it names the Chat SDK and not UIKit, for example "Chat SDK", "sendbirdChat", "SendbirdChat", "@sendbird/chat", `--product chat`, "without UIKit", or "UIKit 없이".
     - `chat-ui=uikit` (and `chat` in `products`) when it names UIKit, for example "UIKit" or `--product uikit`.
     - `products`: the products it names: `chat` for a chat app, chat screens, or messaging, and `calls` for voice or video calls or `--product calls`. When it names only one of the two, `products` is that one.
     - A `chat=` answer puts `chat` in `products`, and a `calls=` answer puts `calls` in `products`.
     - An `answers:` value wins over what the message implies.
   - Interactive: ask with AskUserQuestion (in Codex, request_user_input when it is listed), using the catalog's question text and option labels as written (translated into the customer's language if needed). With neither tool, or when request_user_input returns no answer, ask in your reply and stop until the customer answers; do not pick an answer for them. Use `multiSelect` for `multi` questions. Ask `products` first, then `chat-ui` and `platform` together, then the rest (at most 4 questions per call). Do not add, drop, or reword options.
   - Non-interactive (`SENDBIRD_NONINTERACTIVE`): read answers from the request, written as `answers: products=chat,calls; chat-ui=uikit; platform=react; chat=channel-list,conversation; calls=voice-call; notes=...`. Besides the catalog questions, an answer may be `confirm-<feature-id>=yes` or `confirm-<feature-id>=no`, where `<feature-id>` is an `id` in `core/plans.json`: it answers the plan confirmation from step 3. Any other answer that is not a catalog option id is an error. If the request has no answers yet, change nothing and stop with `status: "needs_input"`, returning every catalog question in scope that the request does not already answer, at once, in catalog order, each with its `id`, `question`, `type`, option ids as `options`, the option labels as `labels` (same order), and `when` when it has one, so the caller can ask them all and run again once (with `--resume` it continues this session). If answers are given but a `required` question that applies is missing, return only the missing ones the same way. The caller sees only the returned questions, so when a returned question's `when` names a question the request already answers (or a one-option question), drop that condition when it holds, and leave the question out when it does not. When `SENDBIRD_LOCALE` is set (a language such as `ko` or `ja`), write `question` and `labels` in that language; never translate `id`, `options`, or `when`, since the caller passes answers back by option id.
3. Check the plan before writing any file. The plan is the `plan` answer; without one, it is what `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/resolve-plan.sh" <project-dir>` prints (`SENDBIRD_PLAN`, otherwise `unsure`). For each feature the `chat` or `notes` answers ask for that is listed in `core/plans.json`, run `SENDBIRD_PLAN=<plan> bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/resolve-plan.sh" <project-dir> --check <feature-id>` and follow `knowledge/curated/common/plans.md`: build `ok` features, show the message for `sales` features and leave them out, and for `confirm` features:
   - Interactive: show the message and ask with "Add it" and "Leave it out".
   - Non-interactive: use the request's `confirm-<feature-id>` answer (`yes` builds it, `no` leaves it out). If a `confirm` feature has no answer, change nothing (no starter, no profile) and stop with `status: "needs_input"`, returning one question per such feature: id `confirm-<feature-id>`, the decision's `message` as `question`, `type` `single`, options `["yes", "no"]`, and `labels` `["Add it", "Leave it out"]` (in `SENDBIRD_LOCALE` when it is set). The caller runs again with the same answers plus `confirm-<feature-id>=yes` or `confirm-<feature-id>=no`.
4. Copy the starter named by `starters` in the catalog (`platform`, or `platform/<ios-ui|android-ui>`) from `${CLAUDE_PLUGIN_ROOT}/` into the project folder, then initialize git if the folder is not a repository.
   - React Native: `templates/starters/react-native` already has its `ios/` and `android/` native projects (React Native 0.87.1, made with the React Native CLI; see its `_README.md`), so the app runs on a simulator or emulator. Copy them with the rest; never report native folders as missing, and never make them again. Its `ios/Podfile` is React Native's own CocoaPods setup, not a Sendbird iOS SDK install, so the SPM-first rule does not apply to it. This run does not install pods: running on iOS (`cd ios && pod install`, then `npm run ios`) is part of the device or simulator run.
   - Pick the starter by the `products` and `chat-ui` answers from step 2 (which already read the SDK the request names):
     - `chat-ui=chat-sdk`: copy only the catalog starter above and build every screen on the Chat SDK: never start from `templates/starters-bp/` (its screens are UIKit) and never install a UIKit package. Tell the customer the app uses the Chat SDK without UIKit.
     - `chat-ui=uikit`: start from `${CLAUDE_PLUGIN_ROOT}/templates/starters-bp/<host>/` instead (`react`, `react-native`, `ios-uikit`, `ios-swiftui`, `android-view`, `android-compose`): sign-in, connect, channel list, channel screen, and sign-out are already wired there. Read that folder's `_README.md` first, keep the practices listed in `templates/starters-bp/BEST_PRACTICES.md`, and tell the customer which starter was used. `starters-bp/react-native` also has its `ios/` and `android/` native projects (React Native 0.87.1, the same native projects as the plain starter plus the native setup UIKit's modules need); the same rules apply. It starts without push until the customer adds their Firebase project files (a `manualSteps` entry).
     - `products=calls` alone (no Chat): copy only the catalog starter above and install the Calls SDK alone, with no Chat SDK, no UIKit, and no Chat connect. Calls signs users in on its own: the Calls Authentication page says Calls needs its own authentication even when the app already uses Chat, and the Calls getting-started page installs only the Calls SDK and says the Chat and Calls SDKs can be used together (https://sendbird.com/docs/calls/sdk/v1/javascript/features/authentication , https://sendbird.com/docs/calls/sdk/v1/javascript/getting-started/make-first-call). The starter's `onLoginSucceeded` authenticates to Calls and its `onLogout` deauthenticates, as the host's `templates/<platform>/<host>/calls/_README.md` describes. Never start from `templates/starters-bp/` (its screens are Chat UIKit).
5. Save the `plan` answer as `plan` in `.sendbird-client/profile.json` (`unsure` when it was not answered).
6. Continue with Steps 2–5 above: App ID (on JS with an env loader, written to `.env.local`, which the starters ignore in `.gitignore`; never to `.env`), then the platform agent implements sign-in and connect in the starter's `onLoginSucceeded` and `onLogout` (in a Calls-only app, the Calls authenticate and deauthenticate instead of the Chat connect), then every chosen feature that step 3 kept, and shows each on screen. A feature built after a confirmation goes under `manualSteps` as needing the plan in `requiredPlan`. Install packages as the agent contract requires. This run does not build or type-check the project (contract section 3); the answer may say so once in its text, never as a `manualSteps` entry.
7. Write the run summary (`core/schemas/run-summary.schema.json`, with `skill: "setup"`) to the path in `SENDBIRD_RUN_SUMMARY_FILE` when it is set, in both modes, so the caller can read the result after the session ends. List the answers used under `steps`.

## Wired knowledge (read these FIRST — populated and cited)
- Install coordinates + packaging policy: `knowledge/curated/<platform>/setup.md` (iOS is SPM-first).
- Plan-limited features and the confirm-before-adding rule: `knowledge/curated/common/plans.md` (data in `core/plans.json`).
- Product init/connect/send: `knowledge/curated/<platform>/products/<product>.md` (chat/uikit/calls — all populated; iOS snippets build-verified, JS type-checked).
- Verified splice code: `templates/ios/uikit/{chat/InitConnect.swift, uikit/SetupUIKit.swift, calls/SetupCalls.swift}` and the matching `templates/android/view/...`, `templates/js/react/...`, `templates/js/react-native/...` files (each `_README.md` documents splice steps).
- Chat features a request names (for example in `notes`): images and files, edit and delete, unread counts, typing indicator, and read receipts have verified files on every host under `templates/<platform>/<host>/chat/` (feature table in `skills/add-feature/SKILL.md`; splice steps in that folder's `_README.md`).
- Calls (`--product calls`, or the catalog `calls` answers `voice-call` and `video-call`): `templates/<platform>/<host>/calls/`. Its `_README.md` lists the install, the camera and microphone permissions (Info.plist usage strings, Android runtime permissions, the browser prompt), initialize at startup, authenticate in `onLoginSucceeded` after the Chat connect (a Calls-only app has no Chat connect; New app step 4), deauthenticate in `onLogout`, and a call screen that dials a user ID and accepts or declines a ringing call. React has that screen ready: `templates/js/react/calls/DirectCallPanel.tsx`. On iOS, Android, and React Native, incoming calls need push even while the app is open (the iOS and Android Authentication docs, "WebSocket"); dialing out does not. Push needs VoIP or FCM credentials in the dashboard and a real device, so list it under `manualSteps` and point to `/sendbird-client:calls-incoming`. The web SDK receives calls while its WebSocket is connected. Calls `manualSteps` hold only the steps in the product file's "Manual steps" section (App ID, a token server when the app uses tokens, push credentials); no Calls doc has a dashboard step that enables Calls, so never write one.
- Non-native hosts (SwiftUI/Compose): the host `_README.md` under templates explains the verified interop path — no host-native SDK API exists; do not invent one.

## No-Fabrication
The platform agent emits only verified API (from knowledge/curated, customer-local SDK, the public mirror, or sendbird.com/docs), citing each symbol. If a needed API can't be verified, it says "I don't know — here's what I checked" and stops. No invented SDK calls.
