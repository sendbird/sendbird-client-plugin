# /sendbird-client:setup

A request to create a Sendbird application itself (the application on the Sendbird Dashboard that gets an App ID, for example "Sendbird에 새 애플리케이션 만들어 줘" or "create a new Sendbird application"), not app code, is not setup: change nothing, run no detection, and say that this plugin writes app code and does not create Sendbird applications. When the session lists a Sendbird CLI plugin skill, use that skill for it; otherwise point to the Sendbird Dashboard (do not guess a URL or a menu path). A request that names a platform, a project, or screens ("채팅 앱 만들어 줘", "a chat web page") is app code and stays here.

Interactive first-integration wizard.

Resolve every plugin-owned path below from `${CLAUDE_PLUGIN_ROOT}`. Where that variable is empty (Codex does not set it for shell commands), the plugin root is the folder two levels above this SKILL.md.
Resolve the platform agent with `bash "${CLAUDE_PLUGIN_ROOT}/tools/routing/route-agent.sh" <project-dir> code`. Hand work to that agent by calling the `Agent` tool once with the agent as Claude Code lists it: this plugin's name, a colon, then the name the router printed (for example `sendbird-client:sendbird-ios-agent`). In Codex, which has no `Agent` tool, run that agent's launcher skill instead (for example `$sendbird-client:sendbird-ios-agent`) and start the agent only as that skill says; it sets the model and settings the agent needs. Do not do the agent's part yourself, even in a small project: write or edit no project source file in this session, before or after the hand-off, also when the customer confirms a change in a later turn. If the hand-off fails, say that this part was not done. When the agent reports, your final answer carries its changed files, every check line, and its symbol, source, and version table as the agent wrote them (`docs/AGENT_CONTRACT.md` section 6); shorten the wording only. Copying the starter ("New app" step 4) and writing `profile.json` and the run summary are this skill's own steps.
Before anything else, check every product the request names (AI Agent, its messenger or launcher, is `ai-agent`; the others are `chat`, `uikit`, `calls`, `desk`, and `live`) with `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/resolve-products.sh" <project-dir> --check <product>`, one run per product. Printing the scope without `--check` is not this check. When it exits 1, change nothing and hand nothing to an agent: say what it printed. Only for "out of configured scope" add that `SENDBIRD_PRODUCTS` or `enabledProducts` in `.sendbird-client/profile.json` sets the scope; for "not available on this host" give the reason it printed and never suggest those settings, which cannot change it; a non-interactive run ends with `status: "declined"`.

## Steps
1. Detect the project: run `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/detect.sh" <project-dir>` every time. Resolve platform, host, packageManager, deploymentTarget, lifecycle, products. If any Tier-1 fact is `unknown` or host is `hybrid`, ASK the customer once — never guess.
2. Resolve `app_id`: env `SENDBIRD_APP_ID` > `.sendbird-client/profile.json` (`appId` field) > ask. The first that has a value wins, so a conflict needs no question: when `SENDBIRD_APP_ID` and `profile.json` hold different App IDs, take the `SENDBIRD_APP_ID` value without asking and say so in one line. Whatever its source (`SENDBIRD_APP_ID`, the request, or the customer's answer), **persist** the App ID you use as `appId` in `.sendbird-client/profile.json` before the hand-off, keeping the fields detect.sh wrote: `jq --arg a <app-id> '.appId = $a' .sendbird-client/profile.json > .sendbird-client/profile.json.tmp && mv .sendbird-client/profile.json.tmp .sendbird-client/profile.json`. Then it is asked only once per project — App IDs are not secret. `profile.json` is the plugin's own record; how the app's code reads the App ID stays the agent's choice (step 3). NEVER store session/access tokens anywhere (tokens stay in env at runtime).
   - To find out where the App ID comes from, run `bash "${CLAUDE_PLUGIN_ROOT}/tools/detection/resolve-app-id.sh" <project-dir>`. It checks `SENDBIRD_APP_ID` and then the profile's `appId`, in the order above, and prints `{"from":"env"}`, `{"from":"profile"}`, or `{"from":"missing"}`, never the value. Ask for the App ID only when it prints `missing`. Whether the App ID is there is decided by that `from` value alone: never by reading `profile.json` or the environment yourself and judging the value (an all-zero or example-looking App ID that the tool reports as `profile` or `env` is set, and is not asked for again). Do not decide it is missing from `printenv SENDBIRD_APP_ID` alone: a profile that already has `appId` answers it. When you need the value, read it from the source it names (`printenv SENDBIRD_APP_ID`, or `jq -r .appId .sendbird-client/profile.json`).
   - To see which `SENDBIRD_*` variables are set, list names only with `env | sed -n 's/^\(SENDBIRD_[A-Z0-9_]*\)=.*/\1/p'` (a token such as `SENDBIRD_API_TOKEN` may be among them). Read each value you need with its own `printenv <NAME>`: macOS `printenv` reads only the first name, so `printenv SENDBIRD_NONINTERACTIVE SENDBIRD_APP_ID` never shows the App ID.
3. Hand off to the platform agent (`sendbird-ios-agent` / `sendbird-android-agent` / `sendbird-js-agent`) for code edits. Pass the customer's request and the detected facts. Leave the install and the App ID mechanism to the agent, which follows `docs/AGENT_CONTRACT.md` section 3, and keep its choices on those when it returns.
4. The agent installs the SDK dependency, inserts initialize + connect in the correct lifecycle entry, and (optionally) scaffolds a first screen from `templates/<platform>/<host>/<product>/`.
   - iOS: install via Swift Package Manager. Use CocoaPods only if the project already has a `Podfile`; never create one or run `pod install` on a fresh/SPM project.
   - If the project already uses Chat SDK v3 or UIKit v2, ask the customer whether to upgrade first, and follow `knowledge/curated/<platform>/cross-cutting/migration.md` when they agree.
5. Report as `docs/AGENT_CONTRACT.md` section 6 lists: the changed files, each section 4 check as pass, fail, or not run, the symbol-to-source table, and a product-specific next-step checklist. When the request named no SDK, say which one was used (UIKit or the Chat SDK) and why. End the answer text by suggesting `/sendbird-client:verify-integration` to check the integration and `/sendbird-client:run-check` to build and launch the app; only suggest them, this skill does not build or launch the app. In a non-interactive run, list both under `nextSteps` and the checks under `checks`.

## New app (empty folder)
Use this when the request is to create a new app, or the project folder is empty (detection finds no platform). The app starts from the catalog starter in step 4, never from a project generator such as `npm create vite`, `create-react-app`, or `create-next-app`: the starters already have the sign-in code (`onLoginSucceeded`, `onLogout`) that the rest of setup fills in.

1. Read the questions from `${CLAUDE_PLUGIN_ROOT}/core/catalog.json`. Drop options whose `product` is outside the active scope (`resolve-products.sh`), and drop a question with no options left. Skip a question whose `when` does not match the answers so far; a `when` on a `multi` answer matches when any chosen option is listed (`products=chat,calls` matches `"when": { "products": ["chat"] }`). A `required` question with one option left is not asked: that option is its answer (for example `products` when the scope has Chat but not Calls, or `chat-ui` when UIKit is out of scope). Leave out a question with `"offered": false`; that feature is not offered in new-app setup for now. If the request itself names that feature (for example in `notes`), build it as usual, unless its product is not supported yet (`resolve-products.sh --check <product>` reports `not supported yet`); that product is declined, never built.
2. Get the answers:
   - Answers the request already gives. The request is the customer's own message, not only the arguments this skill was started with: those can leave the SDK name out, so read both. Do not ask a question the request already answers:
     - `chat-ui=chat-sdk` (and `chat` in `products`) when it names the Chat SDK and not UIKit, for example "Chat SDK", "sendbirdChat", "SendbirdChat", "@sendbird/chat", `--product chat`, "without UIKit", or "UIKit 없이".
     - `chat-ui=uikit` (and `chat` in `products`) when it names UIKit, for example "UIKit" or `--product uikit`.
     - `products`: the products it names: `chat` for a chat app, chat screens, or messaging, and `calls` for voice or video calls or `--product calls`. When it names only one of the two, `products` is that one.
     - A `chat=` answer puts `chat` in `products`, and a `calls=` answer puts `calls` in `products`.
     - `platform`: the platform it names. A web app or web page is `platform=react`, for example "web", "web page", "웹", "채팅웹", "웹 페이지", or "React" (not React Native); "React Native" is `react-native`, "iOS" or "iPhone" is `ios`, and "Android" is `android`. Do not return the `platform` question when the request names one of these, also in a non-interactive run whose `answers:` leave `platform` out.
     - An `answers:` value wins over what the message implies.
   - Interactive: ask with AskUserQuestion (in Codex, request_user_input when it is listed), using the catalog's question text and option labels as written (translated into the customer's language if needed). With neither tool, or when request_user_input returns no answer, ask in your reply and stop until the customer answers; do not pick an answer for them. Use `multiSelect` for `multi` questions. Ask `products` first, then `chat-ui` and `platform` together, then the rest (at most 4 questions per call). Asking in your reply follows the same groups: one group per reply, then stop until the customer answers, and ask optional questions too instead of answering them yourself. Do not add, drop, or reword options.
   - Non-interactive (`SENDBIRD_NONINTERACTIVE`): read answers from the request, written as `answers: products=chat,calls; chat-ui=uikit; platform=react; chat=channel-list,conversation; calls=voice-call; notes=...`. An answer that is not a catalog option id is an error. If the request has no answers yet, change nothing and stop with `status: "needs_input"`, returning every catalog question in scope that the request does not already answer, at once, in catalog order, each with its `id`, `question`, `type`, option ids as `options`, the option labels as `labels` (same order), and `when` when it has one, so the caller can ask them all and run again once (with `--resume` it continues this session). Add the `app-id` question from step 3 when there is no App ID. If answers are given but a `required` question that applies is missing, return only the missing ones the same way. The caller sees only the returned questions, so when a returned question's `when` names a question the request already answers (or a one-option question), drop that condition when it holds, and leave the question out when it does not. When `SENDBIRD_LOCALE` is set (a language such as `ko` or `ja`), write `question` and `labels` in that language; never translate `id`, `options`, or `when`, since the caller passes answers back by option id.
3. Check the App ID before writing any file: resolve it now as step 2 above does (`resolve-app-id.sh`, an App ID the request gives). Interactive: ask for it now when `resolve-app-id.sh` prints `missing` and the request gives none. Non-interactive: when none has it, change nothing (no starter, no profile) and stop with `status: "needs_input"` and one question with id `app-id` that asks for it through `SENDBIRD_APP_ID`.
4. Copy the starter named by `starters` in the catalog (`platform`, or `platform/<ios-ui|android-ui>`) from `${CLAUDE_PLUGIN_ROOT}/` into the project folder, then initialize git if the folder is not a repository.
   - React Native: `templates/starters/react-native` already has its `ios/` and `android/` native projects (React Native 0.87.1, made with the React Native CLI; see its `_README.md`), so the app runs on a simulator or emulator. Copy them with the rest; never report native folders as missing, and never make them again. Its `ios/Podfile` is React Native's own CocoaPods setup, not a Sendbird iOS SDK install, so the SPM-first rule does not apply to it. This run does not install pods: running on iOS (`cd ios && pod install`, then `npm run ios`) is part of the device or simulator run.
   - Pick the starter by the `products` and `chat-ui` answers from step 2 (which already read the SDK the request names):
     - `chat-ui=chat-sdk`: copy only the catalog starter above and build every screen on the Chat SDK: never start from `templates/starters-bp/` (its screens are UIKit) and never install a UIKit package. On React, give the screens the stable test ids that `templates/js/react/chat/_README.md` names (`sb_channel_list`, `sb_message_input`, and the others), so a later run check finds them. On React Native, every screen with a message input at the bottom (the conversation, a thread) has `templates/js/react-native/chat/KeyboardAvoidingScreen.tsx` as its root, so the keyboard does not cover the input (`knowledge/curated/js/hosts/react-native.md` "Keyboard over the message input"). Tell the customer the app uses the Chat SDK without UIKit.
     - `chat-ui=uikit`: start from `${CLAUDE_PLUGIN_ROOT}/templates/starters-bp/<host>/` instead (`react`, `react-native`, `ios-uikit`, `ios-swiftui`, `android-view`, `android-compose`): sign-in, connect, channel list, channel screen, and sign-out are already wired there. Read that folder's `_README.md` first, keep the practices listed in `templates/starters-bp/BEST_PRACTICES.md`, and keep the starter's code as it is when adding to it: every `BPxx` marker line stays, and so does its session handler (BP04, the token refresh hook), which contract section 3's rule on session handlers does not remove. Tell the customer which starter was used. `starters-bp/react-native` also has its `ios/` and `android/` native projects (React Native 0.87.1, the same native projects as the plain starter plus the native setup UIKit's modules need); the same rules apply. It starts without push until the customer adds their Firebase project files (a `manualSteps` entry). On every host, put each item of the "Not included" section of `BEST_PRACTICES.md` (push credentials and the notification permission prompt, a token server) under `manualSteps`, and keep the dependency versions the starter pins: do not upgrade them or run `npm audit fix`.
     - `products=calls` alone (no Chat): copy only the catalog starter above and install the Calls SDK alone, with no Chat SDK, no UIKit, and no Chat connect. Calls signs users in on its own: the Calls Authentication page says Calls needs its own authentication even when the app already uses Chat, and the Calls getting-started page installs only the Calls SDK and says the Chat and Calls SDKs can be used together (https://sendbird.com/docs/calls/sdk/v1/javascript/features/authentication , https://sendbird.com/docs/calls/sdk/v1/javascript/getting-started/make-first-call). The starter's `onLoginSucceeded` authenticates to Calls and its `onLogout` deauthenticates, as the host's `templates/<platform>/<host>/calls/_README.md` describes. Never start from `templates/starters-bp/` (its screens are Chat UIKit).
5. Save the App ID from step 3 as `appId` in `.sendbird-client/profile.json`.
6. Continue with Steps 2–5 above (step 5's report and suggestions included): the App ID step 3 resolved, written where the project reads it (on JS with an env loader, written to `.env.local`, which the starters ignore in `.gitignore`; never to `.env`), then the platform agent implements sign-in and connect in the starter's `onLoginSucceeded` and `onLogout` (in a Calls-only app, the Calls authenticate and deauthenticate instead of the Chat connect) and, when the starter has no sign-in screen, adds one: a user ID text field and a sign-in button shown on the first screen itself (not behind another button or in an alert), with the field empty (no prefilled or example ID), whose button calls `onLoginSucceeded` with the typed ID. The app never signs in a fixed user ID at launch, also when the request names one user (for example a seller ID, which is the other side of the chat), and the sign-in screen is built in this run, never left to the customer as a to-do; then every chosen feature, and shows each on screen. Install packages as the agent contract requires. This run does not build the project (contract section 3); the answer may say so once in its text, never as a `manualSteps` entry. With `chat-ui=chat-sdk`, the brief tells the platform agent to type-check the screens it wrote once they are written: `bash "${CLAUDE_PLUGIN_ROOT}/tools/verify/check-written.sh" <project-dir> <every .ts, .tsx, .kt, .java, and .swift file written>`, fix the errors it lists in those files, and run it again, up to three runs (contract section 3, "Type-check the Chat SDK screens you wrote"). Report its last result as the check `typecheck` (pass, fail, or not run with its `reason`, plus its `tool` and `seconds`). The UIKit path (`chat-ui=uikit`, `templates/starters-bp/`) and a Calls-only app do not run it.
7. Write the run summary (`core/schemas/run-summary.schema.json`, with `skill: "setup"`) to the path in `SENDBIRD_RUN_SUMMARY_FILE` when it is set, in both modes, so the caller can read the result after the session ends. List the answers used under `steps`.

## Wired knowledge (read these FIRST — populated and cited)
- Install coordinates + packaging policy: `knowledge/curated/<platform>/setup.md` (iOS is SPM-first).
- Product init/connect/send: `knowledge/curated/<platform>/products/<product>.md` (chat/uikit/calls — all populated; iOS snippets build-verified, JS type-checked).
- Verified splice code: `templates/ios/uikit/{chat/InitConnect.swift, uikit/SetupUIKit.swift, calls/SetupCalls.swift}` and the matching `templates/android/view/...`, `templates/js/react/...`, `templates/js/react-native/...` files (each `_README.md` documents splice steps).
- Chat features a request names (for example in `notes`): images and files, edit and delete, unread counts, typing indicator, and read receipts have verified files on every host under `templates/<platform>/<host>/chat/` (feature table in `skills/add-feature/SKILL.md`; splice steps in that folder's `_README.md`).
- Calls (`--product calls`, or the catalog `calls` answers `voice-call` and `video-call`): `templates/<platform>/<host>/calls/`. Its `_README.md` lists the install, the camera and microphone permissions (Info.plist usage strings, Android runtime permissions, the browser prompt), initialize at startup, authenticate in `onLoginSucceeded` after the Chat connect (a Calls-only app has no Chat connect; New app step 4), deauthenticate in `onLogout`, and a call screen that dials a user ID and accepts or declines a ringing call. React has that screen ready: `templates/js/react/calls/DirectCallPanel.tsx`. On iOS, Android, and React Native, incoming calls need push even while the app is open (the iOS and Android Authentication docs, "WebSocket"); dialing out does not. Push needs VoIP or FCM credentials in the dashboard and a real device, so list it under `manualSteps` and point to `/sendbird-client:calls-incoming`. The web SDK receives calls while its WebSocket is connected. Calls `manualSteps` hold only the steps in the product file's "Manual steps" section (App ID, a token server when the app uses tokens, push credentials); no Calls doc has a dashboard step that enables Calls, so never write one.
- Non-native hosts (SwiftUI/Compose): the host `_README.md` under templates explains the verified interop path — no host-native SDK API exists; do not invent one.

## No-Fabrication
The platform agent emits only verified API (from knowledge/curated, customer-local SDK, the public mirror, or sendbird.com/docs), citing each symbol. If a needed API can't be verified, it says "I don't know — here's what I checked" and stops. No invented SDK calls.
